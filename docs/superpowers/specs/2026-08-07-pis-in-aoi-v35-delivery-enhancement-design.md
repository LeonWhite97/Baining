## 1. 设计目标

在不修改 PIS-IN AOI 旁路复判核心架构的前提下，将现有 V3.5 资料扩展为一套可说明、可演示、可部署、可追溯的完整项目交付包。

本次增强必须同时解决四类问题：

1. 项目文档缺少统一的项目背景、功能模块、业务流程、数据流、技术架构和部署说明。
2. Agent、RAG、团队、周期、预算和算力缺少清晰且可解释的口径。
3. 现有项目展示以 PDF 为主，缺少可实际运行的前端与后端演示系统。
4. 个人工作内容尚未系统转换为可验证成果和求职竞争优势。

### 2.3 综合误报率目标口径

综合误报率以原 AOI NG 候选池为统计范围：

```text
综合误报率 =
原 AOI 判为 NG、但经人工复核确认为正常的数量
÷ 原 AOI NG 候选总数
```

项目采用分阶段目标：

| 阶段 | 综合误报率目标 | 定位 |
|---|---:|---|
| 原 AOI 基线 | 12% | 当前问题基线 |
| PoC 验收 | ≤6% | 证明方案有效，相对基线下降至少 50% |
| 影子运行/受控上线 | ≤3% | 项目主要交付目标，相对基线下降至少 75% |
| 成熟生产阶段 | ≤1.5% | 持续优化方向，不作为当前已实现结果 |

如果按全部检测产品为分母统计，则应单独命名为“全检件误报率”，建议目标不高于 0.5%，不得与 NG 候选池综合误报率混用。

综合误报率下降必须与关键缺陷召回率、自动 PASS 漏放率和 REVIEW 比例同时报告，不能用降低误报掩盖漏放风险。

### 2.4 标准估算口径

GPU、存储、预算比例和阶段人月作为标准 PoC 估算展示，必须明确标注为推荐配置或估算值。

### 2.5 待现场验证口径

本现场的缺陷召回率、自动 PASS 漏放率、误报过滤率、REVIEW 比例、端到端 P95、持续吞吐和静默错配率必须通过真实数据审计、独立盲测和影子运行确定。

## 3. 架构边界

### 3.1 保持不变的核心架构

```text
PIS-IN 数据输出
→ 数据适配与确定性 Source Key 关联
→ 文件身份、完整性、时间偏差和 Hash 校验
→ FastAPI 实时服务
→ YOLOv8 / TensorRT 推理
→ 3D 后融合与物理规则
→ PASS / FAIL / REVIEW
→ PostgreSQL、MES、Tray Map、报表和审计
```

核心原则：

- 原 AOI 继续承担机械流程和基础检测职责。
- AI 作为旁路复判层，故障时不阻塞原 AOI。
- LangGraph、Agent 和 RAG 不进入单件实时推理关键路径。
- 未知、缺失、错配和低置信度样本不能自动 PASS。

### 3.2 新增的增强能力

- React 可运行前端。
- FastAPI 演示接口与 AOI 数据模拟器。
- PostgreSQL 数据持久化和 pgvector 知识检索扩展。
- 3 个 LangGraph Agent 与 1 套 RAG 知识库。
- Docker Compose 一键部署。
- 真实推理适配接口，用于后续挂载 YOLOv8 ONNX/TensorRT Engine。

## 4. 系统总体数据流

```text
PIS-IN 或 AOI 数据模拟器
        |
        v
数据适配层：Source Key、附件汇聚、文件质量、幂等
        |
        v
推理层：YOLOv8 / TensorRT 或模拟推理适配器
        |
        v
决策层：2D 结果 + 3D 数值 + AOI 原结果 + 规则护栏
        |
        v
PASS / FAIL / REVIEW + defect_code + reason_code
        |
        +--> PostgreSQL / Tray Map / 缺陷报表
        +--> 人工复核 / 金标准回流
        +--> 工站预警 / 异常报告
        +--> Agent / RAG 离线治理
        |
        v
React 前端展示与操作
```

## 5. 可运行演示系统

### 5.1 双模式设计

**演示模式**：

- 使用 AOI 数据模拟器持续生成设备、产品、批次、Tray、Slot、2D 缺陷框、3D 数值和 AOI 结果。
- 生成 PASS、FAIL、REVIEW、未知缺陷、文件缺失、工站缺陷率升高等场景。
- 所有页面、复核动作、报表和异常报告使用真实 API 与数据库，不采用静态截图。

**真实模式**：

- 替换数据适配器，读取真实 PIS-IN 文件或接口。
- 挂载 YOLOv8 ONNX/TensorRT Engine。
- 保持前端、业务 API、数据库、Agent/RAG 和报表结构不变。

### 5.2 前端页面

| 页面 | 核心功能 |
|---|---|
| 总览看板 | 设备状态、当前节拍、PASS/FAIL/REVIEW、缺陷趋势、工站告警 |
| 实时检测 | 2D 图像、缺陷框、置信度、3D 数值、原 AOI 结果和理由码 |
| Tray Map | Tray/Slot 热力图、批次追溯、缺陷位置分布 |
| 人工复核 | REVIEW 队列、证据查看、确认/驳回、备注和金标准回流 |
| 缺陷报表 | 按产品、批次、工站、班次、设备、模型和缺陷类别统计 |
| 预警与异常报告 | 预警阈值、证据汇总、确认人、处置状态和报告生成 |
| 模型治理 | 模型版本、影子结果差异、发布状态、审批记录和回退 |
| 项目说明 | 项目背景、功能、流程、架构、技术栈、团队周期、算力和个人成果 |

前端不得展示项目预算、预算比例或内部成本信息。

### 5.3 前端交互要求

- 支持时间、产品、批次、设备、工站、缺陷和状态筛选。
- 实时事件自动刷新，页面布局不因动态数据发生跳动。
- 人工复核动作通过 API 落库，刷新后结果保持。
- Tray Map 可点击槽位查看对应检测详情。
- 预警可确认、关闭和查看关联异常报告。
- 模型页面可查看影子差异和回退记录，不在演示环境执行无审批的生产切换。

## 6. Agent 与 RAG 设计

### 6.1 数据质量 Agent

职责：

- 检查附件缺失、Source Key 冲突、重复文件、时间偏差和异常批次。
- 汇总输入分布变化和数据漂移信号。
- 输出风险事实、证据和建议动作。

边界：不能直接控制实时 PASS/FAIL，也不能自动修复无法证明身份的数据。

### 6.2 人工复核与异常报告 Agent

职责：

- 汇总代表性图片、缺陷框、3D 指标、Tray Map、模型版本和理由码。
- 检索相似历史异常和处置记录。
- 生成异常报告初稿和待确认事项。

边界：根因、责任和最终处置结论由质量或工艺人员确认。

### 6.3 模型治理 Agent

职责：

- 组织新旧模型评估和影子差异统计。
- 检查召回、漏放、P95、吞吐、积压和漂移门禁。
- 生成发布或回退建议，并保存决策证据。

边界：生产模型发布和自动化范围变更必须经过授权审批。

### 6.4 RAG 知识库

知识范围：

- 缺陷字典和判定标准。
- 设备手册与数据字段说明。
- 质量 SOP 和人工复核指南。
- 历史异常报告、处置记录和模型发布说明。

技术实现：

- PostgreSQL + pgvector 存储文档切片、向量和元数据。
- LangGraph 负责检索、证据编排、引用和人工确认流程。
- LLM 通过可替换的 OpenAI-compatible 接口调用本地或企业模型服务。
- RAG 仅用于解释、查询和报告，不参与单件实时放行。

## 14. 异常处理和安全默认值

- 文件未稳定：等待、重试、超时隔离，不读取半文件。
- 身份缺失：进入 `QUARANTINED`，不按时间邻近猜测归属。
- 3D 缺失：进入 `2D_ONLY` 或 REVIEW，默认不自动 PASS。
- 未知缺陷：进入 UNKNOWN/REVIEW，保留证据并回流。
- AI 服务异常：旁路停用，原 AOI 继续运行。
- Agent 或 RAG 异常：不影响实时推理，报告进入待人工补充状态。
- 模型异常：停止扩大自动化范围或回退稳定版本。
